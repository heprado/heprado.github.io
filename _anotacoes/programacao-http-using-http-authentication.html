Esse método é o menos utilizado mas vamos discutir ele mesmo assim pq eu sou teimoso :)

Quando o API Endpoint está utilizando HTTP Authentication, muito provavalmente ele vai te responder 401 Unauthorized, mas se vc olhar nos headers da resposta vai ter lá um Header chamado WWW-Authenticate, esse header te diz que metodo vc deve usar para se autenticar na API.

Acima conseguimos ver isso:

  1. Cliente tenta fazer uma request GET em /users.
  2. Recebe um 401 Unauthorized com o Header WWW-Authenticate falando que é no esquema Basic.
  3. O cliente então manda uma requisição com o Header Authorization com as informações de autenticação.
  4. Resposta do servidor.

Temos vários esquemas de autenticação sendo utilizados mas os mais famosos são:

  • Anonymous(Anemonas), sem autenticação.
  • Basic, string “usuario:senha” encodada em base64.
  • Bearer Token, é a versão de custom authentication que vimos no capitulo passado, o token expira.
  • Digest, usuario e senha hasheados em MD5.
  • Mutual, tanto o cliente e o servidor precisam se autenticar um com o outro.

Proxies

Muitas vezes temos um proxy no meio do caminho, entre nós(Client) e o servidor(API), nesse caso vamos precisar primeiro nos autenticar no proxy e depois na API para isso utilizamos um header:

  1. O Cliente tenta se autenticar e recebe um Proxy-Authenticate header na resposta do proxy.
  2. Assim o cliente sabe que precisa se autenticar com um Token Bearer num Proxy primeiro e depois na API em cima, então ele passa dois headers na request o Proxy-Authorization e o Authorization em si.
  3. O Proxy recebe a requisição autentica o cliente e então passa a requisição para a API com o header Authentication ainda intacto.
  4. A reposta da requisição volta normal.

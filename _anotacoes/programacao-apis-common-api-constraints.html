Queries & Pagination

Quando fazemos uma request HTTP em uma API, ela pode nos voltar poucos dados ou MUITO DADOS MESMO, isso é algo ruim pois provavelmente não vamos usar nem 1% desses dados, para isso utilizamos queries que são passadas na URL da resource:

Podemos traduzir a query recebida na URL do recurso, isso como já aprendemos se da depois do “?”, assim o software do outro lado pode pegar essa query traduzir para comando SQL e fazer pesquisas na base de dados, na query acima estamos fazendo a paginação da resposta através de comando SQL. O problema dessa forma de fazer as coisas é que dependendo do tamanho da base de dados isso pode ser bastante lerdo.

Algumas APIs tomam conta da paginação sozinho, você faz a query e ele já divide em varias paginas caso ela seja muito grande e passa no body da response qual a proxima pagina para você consultar o restante caso precise.

Rate Limiting

Precisamos limitar o numero de requests que um client faz numa API pois sabemos que pessoas na internet vão tentar fazer um DoS na nossa API, o ato de limitar essas requests é chamado de Rate Limiting, temos duas formas de limitar isso:

  • Client-Side, o usuario da API da uma segurada nas requests através do código, geralmente coloca um timer e um numero maximo de retries.

  • Server-Side, o lugar mais comum de se fazer o rate limiting pois nunca sabemos se o usuário é realmente o usuário, podemos fazer isso através de headers HTTP como o X-RateLimit, fazendo uma queue das requests para fazer o load balacing entre os API Endpoints, o Flask por exemplo também possui uma classe na sua library só pra controlar isso, também podemos usar proxies e load balancers.

Caso o cliente passe desse limite que colocamos geralmente respondemos com HTTP 429 Too Many HTTP Requests e ela geralmente vem junto com um header de Retry-After: “Em tanto tempo”.
